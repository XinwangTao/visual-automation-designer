# 用 Tauri 2 + Rust 做一个可视化桌面自动化工具：架构与几个关键取舍

Visual Automation Designer 是一个开源的桌面自动化流程编辑器：前端用 ReactFlow 画流程图，后端用 Rust 执行真实的鼠标键盘与图像匹配。本文讲它的架构分层和开发中做的几个取舍，适合对 Tauri、桌面自动化或"前端状态 ↔ 原生执行"一致性感兴趣的读者。

仓库：https://github.com/1716775457damn/visual-automation-designer

## 分层：一条链路决定正确性

```
React 组件 → hooks → Tauri command → Rust core → platform（屏幕/输入）
```

四层的职责边界：

- **components**：纯渲染与事件接线，不持有业务状态。
- **hooks**：`useFlow` 管流程与节点、`useFlowHistory` 管撤销重做、`useExecution` 管执行状态机、`useImageLibrary` 管参考图。所有可判定的逻辑尽量抽成纯函数，配 Vitest 单测。
- **commands**：`flow.rs` / `execution.rs` / `image_library.rs`，只做参数校验与状态转换，不含算法。
- **core**：流程管理器、校验器、执行引擎、图像匹配、输入模拟；平台相关能力压到 `platform/` 的抽象层里。

这么分的原因很实际：桌面自动化的 bug 十有八九出在"前端以为的状态"和"后端真实状态"不一致。把状态机集中到 hooks、把副作用集中到 core，能少掉一大半这类问题。

## 取舍一：图像匹配而不是元素选择器

主流 RPA 靠元素树定位。问题是它的可用性完全取决于目标软件是否暴露可访问性接口——老式桌面程序、游戏客户端、远程桌面里经常什么都拿不到。

所以执行引擎的基础能力是**截屏 + 模板匹配**：动作节点可以按图片定位，控制节点按"图在不在"分支。代价是匹配阈值需要调、换分辨率要重截参考图；收益是几乎任何能显示在屏幕上的东西都能被驱动。

## 取舍二：坐标要过 DPI 纠偏

同一个点击，在 100% 缩放下是对的，在 150% 缩放下会偏出一截。项目里对显示器缩放比例做了检测与纠正，坐标在进入输入模拟前统一换算。这块没法只靠单测覆盖，属于"必须在真机上验证"的部分，文档里也标了。

## 取舍三：撤销重做只认"编辑动作"

流程编辑里有三类变更：节点增删、连线增删、配置修改。如果每个状态变化都进历史栈，拖拽过程中会产生几十条无意义记录。

现在的做法是把"一次完整的编辑动作"作为历史单位——拖拽结束、配置失焦才提交一条。历史栈与画布状态由 `useFlowHistory` 统一维护，跨编辑会话保留。

## 前端异常不能静默

一个容易被忽略的细节：如果 React 渲染或某个 Promise 崩了，用户看到的就是"点了没反应"，而日志面板里什么都没有。

项目里给窗口的 `error` / `unhandledrejection` 挂了一个桥：上报后端日志文件，同时派发自定义事件给 AppShell，把它变成一条 toast 和一条执行日志。

这个桥最近做了一次改进：改为引用计数安装。原来只在进程入口 `main.tsx` 注册，App 一旦被嵌进别的入口（测试、浏览器预览）异常就又静默了；现在谁挂载谁安装，最后一个卸载者负责摘监听，并且上报通道自身失败也不会再抛——否则会形成"上报失败 → 未处理拒绝 → 再次上报"的循环。

这类"兜底通道自己崩掉"的问题，往往是上线后才被用户发现的。

## 质量门槛

- 前端 228 个 Vitest 用例，CI 跑 `lint`（0 warning）+ `test` + `build`（tsc 类型检查）。
- Rust 侧单元测试与 clippy 在本地跑，`CONTRIBUTING.md` 里写了命令。
- 截图匹配、执行取消、单步这些必须上真机的能力，在文档里单独标为"真机验证项"。

## 可以拿来用的部分

如果你也在用 Tauri 做"编辑器 + 原生执行"这类应用，这几个模块可能直接有用：

- `src/runtimeIssueBridge.ts`：幂等的运行时异常桥。
- `src/hooks/useFlowHistory.ts`：以编辑动作为单位的历史栈。
- `src-tauri/src/platform/`：屏幕捕获与输入模拟的平台抽象。
